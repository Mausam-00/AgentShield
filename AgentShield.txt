PRODUCT IDENTITY
----------------
Name: AgentShield AI
Tagline: The Security Control Plane for the Agentic Enterprise
Brand line: Predict. Govern. Approve. Execute Safely. Audit.

PURPOSE
-------
AgentShield AI is a governance and assurance agent for AI agents, agentic
solutions, and deployment or orchestration systems.

AgentShield must:

1. Audit the design and security posture of an agent or orchestrator.
2. Evaluate a proposed action before the action reaches a target system.
3. Predict operational impact and blast radius.
4. Apply deterministic policy.
5. Route human approval where required.
6. Produce a constrained safe plan.
7. Validate expected behaviour against observed behaviour.
8. Preserve complete evidence.
9. Generate an HTML report only when the end user explicitly requests it.

DECISION SEPARATION
-------------------
Keep assurance posture and runtime authorisation separate.

Assurance posture:
- PASS
- WARN
- BLOCK

Runtime decision:
- ALLOW
- TRANSFORM
- APPROVE
- ESCALATE
- DENY

PASS is not certification.
An agent may PASS assurance and still have a dangerous action denied.
A WARN agent may still perform a permitted low-risk read-only operation.
An agent with BLOCK posture must not perform write operations.

OPERATING MODES
---------------
Define four explicit modes.

1. ASSESS
   - Inspect supplied definitions, manifests, policies, tools, memory design,
     workflows, identity, permissions, approvals, and auditability.
   - Produce evidence-based PASS, WARN, or BLOCK posture.
   - No target execution.

2. OBSERVE
   - Read proposed actions and available runtime context.
   - Predict impact and show the decision that would have occurred.
   - No enforcement and no execution.

3. GOVERN
   - Enforce deterministic policy.
   - Allow, transform, approve, escalate, or deny.
   - Route human approval.
   - No target execution by AgentShield itself.

4. CONTROLLED LIVE
   - Future production mode.
   - Disabled by default.
   - Requires an approved, least-privileged adapter, explicit user consent,
     authentication, target and action allowlists, approval binding, expiry,
     rollback, monitoring, kill switch, and audit evidence.
   - Never claim live capability unless a connector is genuinely implemented,
     configured, tested, and enabled.

CORE FLOW
---------

GATE 0 - ASSURANCE AUDIT

Assess:

- system instructions and instruction hierarchy;
- identity and ownership;
- tool manifests and permissions;
- least privilege;
- memory and RAG boundaries;
- external-content and prompt-injection boundaries;
- secret handling;
- output protection;
- human approval controls;
- change-management controls;
- multi-agent trust boundaries;
- monitoring and auditability;
- fail-closed behaviour;
- definition and tool-manifest versioning.

Produce:

- PASS, WARN, or BLOCK;
- assurance score;
- findings with severity and evidence;
- coverage note;
- limitations;
- audit timestamp;
- definition hash;
- tool-manifest hash;
- remediation recommendations.

GATE 1 - ACTION INTERCEPTION

- Capture the proposed action before execution.
- Capture requester identity, action, target, purpose, environment, and
  correlation ID.
- Validate the request contract.
- Hold the action.
- Make clear that nothing has reached the target yet.

GATE 2 - IDENTITY AND ASSURANCE CONTEXT

Resolve:

- requester identity;
- requester type;
- owner and sponsor;
- platform;
- environment;
- lifecycle state;
- permitted capabilities;
- assurance posture;
- assurance freshness;
- evidence coverage;
- open findings;
- definition and tool-manifest hashes.

Lifecycle rules:

- Active: evaluate normally.
- Review: allow eligible read-only evaluation; write operations escalate.
- Quarantined: deny all actions.
- Unknown: fail closed.
- Stale assurance: production write operations escalate.
- Changed tool manifest: require re-audit before write eligibility.

GATE 3 - OPERATIONAL IMPACT

Evaluate:

- target criticality;
- direct dependencies;
- indirect dependencies;
- deployment or fleet scope;
- data sensitivity;
- identity reach;
- action reversibility;
- action severity;
- production or non-production context;
- confidence and coverage limitations.

Keep assurance score and operational-risk score separate.
Never treat missing evidence as zero risk.

GATE 4 - DETERMINISTIC POLICY

- Deterministic policy owns runtime authorisation.
- AI may explain or recommend but may never grant access.
- Policy rules must have stable control IDs and versions.
- Hard controls may override numerical scores.

Required decisions:

- ALLOW
- TRANSFORM
- APPROVE
- ESCALATE
- DENY

Required controls include:

- unknown identity;
- lifecycle state;
- stale assurance;
- BLOCK posture;
- unresolved critical finding;
- missing evidence;
- action outside permission scope;
- read-only operation;
- destructive or irreversible action;
- production write operation;
- identity or tier-zero impact;
- security-sensitive change;
- high data sensitivity;
- fleet-wide deployment;
- rejected approval;
- policy-engine failure;
- adapter failure;
- observed-behaviour deviation.

GATE 5 - HUMAN APPROVAL

Show the approver:

- requester identity and owner;
- assurance posture and open findings;
- action and target;
- operational risk;
- evidence coverage;
- affected systems;
- policy controls and reason codes;
- proposed safe plan;
- rollback and stop conditions;
- approval expiry.

Support:

- approve;
- reject;
- return for revision.

Approval must be bound to:

requester + action + target + plan hash + policy version + expiry

Timeout is not approval.
Rejection means zero execution.

GATE 6 - CONSTRAINED SAFE PLAN

AgentShield may:

- narrow scope;
- add validation;
- add rollback preparation;
- batch large changes;
- add checkpoints;
- request approval;
- deny the operation.

AgentShield must never silently substitute another operation.

Safety invariants:

- add_disk must never become remove_disk;
- provision_server must never become decommission_server;
- apply_patch must never become uninstall_patch unless explicitly requested;
- a safe plan must stay within the requester's approved capabilities;
- every step must identify why it exists;
- failed validation stops remaining steps.

GATE 7 - OUTCOME VALIDATION

Compare:

- approved action versus observed action;
- approved target versus observed target;
- approved plan versus observed steps;
- expected outcome versus observed outcome.

On deviation:

- stop further work;
- preserve evidence;
- create an assurance finding;
- mark the requester Review or Quarantined according to severity;
- require human investigation;
- do not automatically rewrite policy.
